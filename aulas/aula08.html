Hoje a TechStore vai separar o acesso ao banco em perfis. O site, o time de análise e o desenvolvimento não devem ter as mesmas permissões. Vamos criar esses perfis, testar cada um e defender uma matriz de acessos.

Para que serve esta aula

Você vai entender como o MySQL decide se uma operação é permitida, criar usuários com permissões mínimas e comprovar, com testes, que cada perfil faz só o que deve.

O que vamos observar no seu trabalho

  • Se cada usuário tem só as permissões da sua função.
  • Se você consegue explicar por que a aplicação executa uma procedure sem ter acesso direto às tabelas.
  • Se as mensagens de erro de permissão são o que você previu.
  • Se a matriz de perfis justifica cada permissão concedida.

Antes de começar

Primeiro, conclua os dois itens da Aula 07 que ficaram pendentes. O docente indica quais são no início da aula.

Entre no MySQL como root e confira se existe algum usuário sem nome:

SELECT user, host FROM mysql.user ORDER BY user;

Se aparecer uma linha com usuário vazio, avise o docente antes de seguir. Ela pode interferir nos testes de senha.

Conceitos rápidos

Um usuário no MySQL é o par 'nome'@'host'. Por exemplo, 'app_site'@'%' é o usuário app_site vindo de qualquer host.

As permissões existem em níveis. Você pode dar SELECT em todo o banco (loja_teste.*), só em uma tabela (loja_teste.pedidos) ou só em uma rotina (PROCEDURE loja_teste.sp_registrar_pedido).

Um papel (role) é um conjunto de permissões que você concede a vários usuários de uma vez.

Uma procedure executa com os privilégios de quem a criou, por padrão. Por isso o usuário da aplicação pode registrar um pedido sem ter INSERT na tabela pedidos. Ele precisa apenas de EXECUTE na procedure. Essa é a base do princípio do menor privilégio: dar o mínimo necessário.

1. Criar usuários e papéis (30 min)

Abra o arquivo Aula08_usuarios_techstore.sql no seu repositório (pasta Data/). Execute as seções em ordem como root:

  1. Crie os três usuários: app_site, analista_bi e dev_techstore. Troque as senhas de exemplo pelas que o docente indicar.
  2. Crie os papéis role_aplicacao, role_analista e role_dev.
  3. Preencha o TODO 1: conceda EXECUTE da procedure sp_listar_produtos_categoria ao role_aplicacao.
  4. Preencha o TODO 2: remova o UPDATE de pedidos do role_dev e conceda a ele EXECUTE de sp_atualizar_status_pedido.
  5. Ligue cada usuário ao seu papel e confira com SHOW GRANTS FOR 'role_aplicacao'; e os outros papéis.

Pergunta antes de executar o TODO 2: se o desenvolvedor não pode mudar o status direto na tabela, por qual caminho ele deve mudar?

2. Testar cada perfil (30 min)

Abra dois terminais. Em um, entre como administrador. No outro, entre com o usuário que você quer testar:

docker exec -it mysql-$USER mysql -u app_site -p loja_teste

Rode os comandos da tabela e compare o resultado com o esperado. Se o resultado for diferente, anote a mensagem de erro e pergunte ao colega antes de mudar a permissão.

Usuário Comando Resultado esperado
app_site CALL sp_listar_produtos_categoria('Eletrônicos'); Lista os produtos
app_site SELECT * FROM pedidos; ERROR 1142: SELECT denied
app_site INSERT INTO pedidos (cliente_id, data_pedido, status) VALUES (1, NOW(), 'Pendente'); ERROR 1142: INSERT denied
analista_bi SELECT nome, email FROM clientes LIMIT 2; Lista os clientes (com e-mail)
analista_bi DELETE FROM produtos WHERE id = 999; ERROR 1142: DELETE denied
dev_techstore UPDATE pedidos SET status = 'Entregue' WHERE id = 1; ERROR 1142: UPDATE denied
dev_techstore CALL sp_atualizar_status_pedido(3, 'Entregue'); Permitido, se a transição for válida

Um teste altera a base: CALL sp_registrar_pedido(...) cria um pedido. Se você quiser testá-lo como app_site, rode uma única vez.

3. Por que a procedure funciona sem permissão na tabela? (10 min)

Responda por escrito, com suas palavras: o app_site não tem INSERT em pedidos, mas sp_registrar_pedido grava lá. Por quê? Qual papel a procedure cumpre entre a aplicação e a tabela?

4. Bloquear e desbloquear uma conta (10 min)

Como administrador, bloqueie o dev_techstore:

ALTER USER 'dev_techstore'@'%' ACCOUNT LOCK;

Tente entrar com esse usuário. Depois, desbloqueie:

ALTER USER 'dev_techstore'@'%' ACCOUNT UNLOCK;

5. Matriz de perfis em dupla (30 min)

Em dupla, preencha a matriz. Para cada perfil e cada objeto, escreva o que o perfil pode fazer: L (ler), G (gravar), E (executar rotina), ou — (nada). Justifique em uma frase as permissões que você deu.

Uma das quatro células da matriz deve ter uma justificativa de risco: qual é o pior efeito se aquele perfil for comprometido?
