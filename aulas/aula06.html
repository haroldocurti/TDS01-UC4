Personalize os comandos

Preencha e os comandos e tabelas desta página passam a usar os seus dados. Fica salvo só neste navegador.

Até agora, as suas funções calculavam: frete, desconto, classificação de cliente. Hoje a loja precisa gravar. Quando alguém compra um Monitor, três coisas acontecem: o pedido é criado, o item é registrado e o estoque diminui. Se só duas delas acontecerem, a loja vende produto que não tem, ou cobra um pedido que não existe.

Hoje você escreve procedures: rotinas que gravam dados, e transações, que fazem essas etapas acontecer todas juntas ou nenhuma delas.

Para que serve esta aula: escrever rotinas que alteram o banco com segurança.

O que vamos observar: - se a sua rotina valida os dados antes de gravar; - se ela desfaz tudo quando algo dá errado; - se você consegue explicar o que acontece quando duas sessões mexem no mesmo dado.

1. Ponto de partida

Responda para você mesmo(a), sem consultar nada:

  2. Imagine que o pedido foi gravado, mas o estoque não foi baixado porque o sistema caiu no meio. O que a loja precisa garantir?

3. Parte A: parâmetros IN, OUT e INOUT (20 min)

Uma procedure recebe e devolve valores por três tipos de parâmetro:

Tipo Quem entra Quem sai Exemplo
IN quem chama envia o valor — o id do cliente
OUT — a procedure devolve o valor o número do pedido criado
INOUT envia e recebe envia e recebe um contador que a procedure aumenta

Rode a Parte A do roteiro:

SET @contador = 10;
CALL sp_demo_parametros(7, @dobro, @contador);
SELECT @dobro AS dobro, @contador AS contador;   -- 14 e 11
Parte O que faz
CALL Executa a procedure. Ao contrário de uma função, não é usada dentro de um SELECT.
@dobro e @contador Variáveis de sessão. Guardam o valor que a procedure devolve.
SET p_dobro = ... Dentro da procedure, grava no parâmetro OUT.

Experimente: rode CALL sp_demo_parametros(7, @dobro, @contador); de novo. O que muda? Por quê?

4. Parte B: controle de fluxo (25 min)

A procedure pode decidir o que fazer com IF, CASE e LOOP.

Leia sp_classifica_pedido no roteiro e rode:

CALL sp_classifica_pedido(1, @msg);   SELECT @msg;   -- Concluído
CALL sp_classifica_pedido(3, @msg);   SELECT @msg;   -- Em andamento
CALL sp_classifica_pedido(999, @msg); SELECT @msg;   -- Pedido não existe

Exercício 1: acrescente o status Pendente ao CASE, com a mensagem "Aguardando pagamento". Recrie a procedure com DROP PROCEDURE IF EXISTS e teste com um pedido com esse status (crie um pedido de teste com UPDATE pedidos SET status = 'Pendente' WHERE id = 3;).

Exercício 2: rode sp_contagem(5). Depois, mude o valor para 3 e para 0. O que acontece com 0? Por que o LEAVE vem antes do SET?

Comando O que faz
IF ... THEN ... ELSE ... END IF Escolhe um caminho.
CASE valor WHEN ... THEN ... END CASE Escolhe um caminho conforme o valor.
LOOP ... LEAVE ... END LOOP Repete até um LEAVE sair do laço.

5. Parte C: o desafio, sp_registrar_pedido (60 min, em duplas)

Esta é a rotina principal da aula. Ela registra um pedido de um produto, para um cliente, em uma transação.

O roteiro traz a assinatura pronta e oito TODOs, um para cada passo. Preencha cada um, na ordem:

TODO O que escrever
1 Um DECLARE EXIT HANDLER FOR SQLEXCEPTION com ROLLBACK; e RESIGNAL; dentro de um BEGIN ... END.
2 Se a quantidade for NULL ou menor que 1: SIGNAL com a mensagem "Quantidade deve ser maior que zero".
3 SELECT estado INTO v_uf FROM clientes WHERE id = p_cliente_id;. Se v_uf continuar NULL, SIGNAL com "Cliente não encontrado".
4 SELECT preco, estoque INTO ... FROM produtos WHERE id = ... FOR UPDATE;. Se o preço for NULL, SIGNAL com "Produto não encontrado".
5 Se o estoque for menor que a quantidade, SIGNAL com CONCAT('Estoque insuficiente: restam ', v_estoque, ' unidades').
6 START TRANSACTION;, depois o INSERT do pedido com status 'Processando', e SET p_pedido_id = LAST_INSERT_ID();.
7 O INSERT do item com o v_preco, e o UPDATE que baixa o estoque.
8 SET v_total = fn_total_pedido(p_pedido_id);, SET p_frete = fn_frete(v_uf, v_total); e COMMIT;.

Dicas:

  • Em SIGNAL, a mensagem precisa estar numa variável: escreva SET v_msg = ...; antes.
  • Antes de compilar, leia o SIGNAL do roteiro (ele serve de modelo).
  • Compile o bloco inteiro e confira erros de sintaxe antes de testar.

Teste o caso feliz

CALL sp_registrar_pedido(1, 2, 2, @pedido, @frete);
SELECT @pedido AS pedido, @frete AS frete;

Esperado: um número de pedido novo (28 se você estiver no banco limpo) e frete 15.00 (cliente de SP, total R$ 160 < R$ 300).

Confira o que foi gravado:

SELECT * FROM pedidos WHERE id = @pedido;
SELECT * FROM itens_pedido WHERE pedido_id = @pedido;
SELECT id, estoque FROM produtos WHERE id = 2;   -- estoque diminuiu em 2

Teste os erros: nada pode ser gravado

Rode cada um e anote a mensagem:

CALL sp_registrar_pedido(1, 2, 0, @p, @f);      -- quantidade zero
CALL sp_registrar_pedido(999, 2, 1, @p, @f);    -- cliente inexistente
CALL sp_registrar_pedido(1, 999, 1, @p, @f);    -- produto inexistente
CALL sp_registrar_pedido(1, 10, 99, @p, @f);    -- estoque insuficiente (a Cadeira Gamer tem 5)
SELECT MAX(id) AS ultimo_pedido FROM pedidos;   -- continua sendo o caso feliz

Se o último pedido mudou, a sua transação não está protegendo a gravação. Revise o TODO 1 e o ROLLBACK.

Pergunta de dupla: se o ROLLBACK do handler fosse removido, o que aconteceria no erro de estoque? Teste e explique.

6. Parte D: cancelamento, para ler (15 min)

A procedure sp_cancelar_pedido já vem pronta. Leia com calma e responda em dupla:

  1. Por que o SELECT ... FOR UPDATE está antes do IF? O que aconteceria sem ele?
  2. O UPDATE produtos p JOIN itens_pedido i ... devolve o estoque. Por que ele não precisa de um WHERE com o produto?
  3. A procedure impede cancelar pedido entregue. Por que essa regra mora no banco e não só no site?

Cancele o pedido que você criou no desafio:

CALL sp_cancelar_pedido(@pedido);
SELECT id, estoque FROM produtos WHERE id = 2;   -- voltou ao valor anterior
CALL sp_cancelar_pedido(1);                      -- Pedido já entregue não pode ser cancelado

7. Parte E: duas sessões no mesmo banco (35 min, em duplas)

Esta parte precisa de dois terminais. Cada um abre sua própria sessão no MySQL:

docker exec -it -e MYSQL_PWD="$SENHA" mysql-$USER \
  mysql -uroot --default-character-set=utf8mb4 loja_teste

Uma pessoa da dupla é a sessão A, a outra é a sessão B. Siga a ordem exata de cada experimento. Anote o que cada sessão viu.

E1. Atomicidade: o ROLLBACK desfaz tudo

-- sessão A
START TRANSACTION;
UPDATE produtos SET estoque = estoque - 10 WHERE id = 1;
SELECT estoque FROM produtos WHERE id = 1;     -- anote o valor
ROLLBACK;
SELECT estoque FROM produtos WHERE id = 1;     -- anote o valor

Depois do ROLLBACK, o estoque voltou. Por quê?

E2. Isolamento: a sessão B vê o que a A não confirmou?

Passo Sessão Comando O que você vê
1 A START TRANSACTION; UPDATE produtos SET estoque = 0 WHERE id = 1; (sem COMMIT)
2 B SELECT estoque FROM produtos WHERE id = 1;
3 B SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; e depois o SELECT de novo
4 A ROLLBACK;
5 B SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

No passo 2, a sessão B viu 0 ou o valor antigo? E no passo 3? Por que a diferença?

E3. Deadlock: duas sessões esperando uma pela outra

Passo Sessão Comando
1 A START TRANSACTION; UPDATE produtos SET estoque = estoque - 1 WHERE id = 1;
2 B START TRANSACTION; UPDATE produtos SET estoque = estoque - 1 WHERE id = 2;
3 A UPDATE produtos SET estoque = estoque - 1 WHERE id = 2; (vai esperar a B)
4 B UPDATE produtos SET estoque = estoque - 1 WHERE id = 1;

No passo 4, uma das sessões deve receber ERROR 1213 (40001): Deadlock found. Qual delas? O que a outra sessão pode fazer agora?

Para terminar, cada sessão dá ROLLBACK; (ou COMMIT;, se preferir), e os estoques voltam ao normal.

Conexão com o desafio: o FOR UPDATE do sp_registrar_pedido evita que duas compras simultâneas do último Monitor leiam o mesmo estoque. Como a sessão A e a B se comportariam se as duas chamassem a procedure ao mesmo tempo?

8. Se algo der errado

Mensagem O que fazer
ERROR 1644 (45000) É um SIGNAL da sua procedure. A mensagem diz o motivo. Não é bug, é a validação funcionando.
ERROR 1305 ... FUNCTION ... does not exist Falta fn_frete ou fn_total_pedido no seu banco. Veja a seção 2.
ERROR 1064 perto de END Confira o DELIMITER $$ e o $$ depois do END da procedure.
ERROR 1213 Deadlock found Esperado na E3. A transação da vítima foi desfeita: rode ROLLBACK; nela.
ERROR 1205 Lock wait timeout A sessão B esperou demais pela A. Dê COMMIT ou ROLLBACK na A.
@pedido ou @frete aparecem como NULL A procedure deu erro, ou o TODO 8 não foi escrito. Veja a mensagem anterior.
ERROR 1054 Unknown column Confira o nome da coluna na tabela (SHOW COLUMNS FROM pedidos;).

Regra de convivência: a base é da turma, mas o banco é o seu. Não mexa no mysql- de outras pessoas.
