Backup na prática

Backup lógico, teste de restauração, log binário, erro simulado, recuperação até um ponto no tempo e script com agendamento. Tudo no seu contêiner MySQL 8.4.

Na Aula 12 você desenhou a política de backup da TechStore. Hoje você vai executá-la: fazer o backup, provar que ele restaura, registrar a posição do log, provocar um erro no seu contêiner e recuperar a base até um instante antes dele.

  • Antes de começar5 min
  • Retomada (em dupla)25 min
  • Prática 1: backup30 min
  • Prática 2: critério de aceite e teste de restauração20 min
  • Prática 3: alterações e o marco B20 min
  • Prática 4: erro, desastre e recuperação até o marco B55 min
  • Prática 5: script e agendamento15 min
  • Checkpoint de saída10 min

Como navegar: use as setas ← e → do teclado ou os botões Anterior e Próximo no rodapé. A lista do rodapé leva direto a qualquer slide. Cada bloco de comando tem um botão Copiar.

Abertura

Para que serve esta aula

Um backup só vale se você consegue restaurá-lo. A recuperação até um ponto no tempo mostra que você consegue voltar a um momento escolhido, e não apenas ao último backup.

Ao final, sua equipe terá um backup testado e uma sequência de comandos que outra pessoa consegue repetir.

O que vamos observar no seu trabalho

  • Se o backup terminou por completo e se os marcos estão registrados em arquivo.
  • Se a restauração do backup dá as mesmas contagens da origem (diff sem diferenças).
  • Se a recuperação até o marco B devolve a base ao estado anterior ao erro (RECUPERAÇÃO OK).

Abertura

Cuidado antes de começar

Atenção: comandos destrutivos

Os comandos destrutivos desta aula (UPDATE sem WHERE e DROP DATABASE) valem só para o seu contêiner mysql-SEU_USUARIO. Confira o nome antes de colar qualquer comando.

Dados pessoais

Os backups contêm nome, e-mail e cidade de clientes. Por isso, as pastas da aula ficam fechadas para colegas (chmod 700), e o backup não sai da sua pasta sem necessidade.

Nos comandos, $USER é o seu usuário na VM, e $SENHA é a variável com a senha do root que você define no início. Nenhuma senha aparece escrita nos slides.

Abertura

Termos que vamos usar

  • Backup lógico: o arquivo .sql gerado pelo mysqldump, com os comandos que recriam a base.
  • Log binário (binlog): o registro, em arquivos, de tudo o que foi alterado no banco. Cada evento tem uma posição, um número que identifica o ponto no arquivo.
  • Marco A: o momento do backup. A posição dele está no cabeçalho do arquivo .sql.
  • Marco B: o último instante antes do erro. Você registra a posição dele antes de errar.
  • Recuperação até um ponto no tempo (PITR): restaurar o backup e aplicar o binlog do marco A até o marco B.
A linha do tempo de hoje, em texto

Backup (marco A) → alterações corretas → marco B → erro de propósito → base apagada → restaurar o backup → aplicar o binlog de A até B → base igual ao marco B, sem o erro.

Antes de começar — passo 4tempo previsto: 5 min

Verifique o ambiente

O que faz: pergunta ao MySQL a versão, o estado do log binário e quantas tabelas, rotinas e triggers a base loja_teste tem.

bash
docker exec -e MYSQL_PWD="$SENHA" mysql-$USER mysql -uroot -N -e "
SELECT CONCAT('versao ........ ', VERSION());
SELECT CONCAT('log_bin ....... ', IF(@@log_bin = 1, 'ON', 'OFF'));
SELECT CONCAT('binlog_format . ', @@binlog_format);
SELECT CONCAT('gtid_mode ..... ', @@gtid_mode);
SELECT CONCAT('tabelas ....... ', COUNT(*)) FROM information_schema.tables WHERE table_schema = 'loja_teste';
SELECT CONCAT('rotinas ....... ', COUNT(*)) FROM information_schema.routines WHERE routine_schema = 'loja_teste';
SELECT CONCAT('triggers ...... ', COUNT(*)) FROM information_schema.triggers WHERE trigger_schema = 'loja_teste';"
O que você deve ver

Sete linhas, uma por item. O esperado: versão 8.4.x, log_bin ON, binlog_format ROW, gtid_mode OFF, pelo menos 4 tabelas e nenhum trigger.

Anote quantas rotinas você tem: elas precisam aparecer depois da restauração.

Se não for isso
  • Access denied: a variável SENHA está vazia ou errada. Rode o passo 2 de novo.
  • log_bin OFF, gtid_mode ON ou algum trigger: chame o docente antes de seguir.
Saiu da VM ou a conexão caiu?

Entre de novo e rode, nesta ordem: o read -s do passo 2, o bloco da função contar (Prática 1, passo 1.1) e source ~/backup_techstore/marcos.txt. Tudo volta como estava.

Prática 1 — passo 1.1tempo previsto da Prática 1: 30 min

Função de contagem

O que faz: cria o comando contar, que conta as linhas das quatro tabelas e os pedidos por status. Você vai usá-lo durante a aula toda.

Cole o bloco inteiro de uma vez.

bash
contar() {
  docker exec -e MYSQL_PWD="$SENHA" mysql-$USER mysql -uroot -N "${1:-loja_teste}" -e "
SELECT 'clientes', COUNT(*) FROM clientes
UNION ALL SELECT 'produtos', COUNT(*) FROM produtos
UNION ALL SELECT 'pedidos', COUNT(*) FROM pedidos
UNION ALL SELECT 'itens_pedido', COUNT(*) FROM itens_pedido;
SELECT CONCAT('status ', status), COUNT(*) FROM pedidos GROUP BY status ORDER BY status;"
}
O que você deve ver

Nenhuma mensagem. A função fica guardada na sessão do terminal. Se você sair da VM, cole este bloco de novo.

Sem argumento, contar usa a base loja_teste. Com um nome depois dele (por exemplo, contar loja_teste_restaurada), conta outra base.

Prática 1 — passo 1.2tempo previsto da Prática 1: 30 min

Backup com mysqldump

O que faz: gera o backup lógico da loja_teste num arquivo .sql com data e hora no nome, guardado na variável BKP.

bash
BKP=~/backup_techstore/loja_teste_$(date +%F_%H%M).sql
docker exec -e MYSQL_PWD="$SENHA" mysql-$USER mysqldump -uroot \
  --single-transaction --routines --triggers --events --source-data=2 \
  loja_teste > "$BKP"
OpçãoO que faz
--single-transactionLê as tabelas InnoDB numa transação, como uma foto do banco, sem bloquear quem está usando a loja.
--routinesInclui as funções e procedures (fn_*, sp_*). Sem esta opção, elas ficam de fora.
--triggers e --eventsIncluem triggers e eventos agendados, se houver.
--source-data=2Escreve no arquivo, como comentário, o nome e a posição do log binário no momento do backup (o marco A).
O que você deve ver

Nenhuma mensagem. O prompt volta depois de alguns segundos. A conferência do arquivo vem no próximo passo.

Faça o backup uma vez só

Se precisar refazer, comece de novo por este passo. O marcos.txt é sobrescrito e os passos seguintes usam os novos valores.

Prática 1 — passo 1.3tempo previsto da Prática 1: 30 min

Conferir o arquivo e ler o marco A

O que faz: mostra o tamanho do backup, a última linha dele e a linha do cabeçalho com a posição do log binário.

bash
ls -lh "$BKP"
tail -n 1 "$BKP"
grep -n "SOURCE_LOG" "$BKP"
O que você deve ver
  • O arquivo com algumas dezenas de KB.
  • A última linha: -- Dump completed on ...
  • A linha do grep, parecida com esta: -- CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='binlog.000003', SOURCE_LOG_POS=1577;

Os números do seu arquivo serão outros. Esse é o seu marco A.

Prática 1 — passo 1.3tempo previsto da Prática 1: 30 min

Guardar o marco A em marcos.txt

O que faz: lê do cabeçalho o arquivo de log (ARQ_A) e a posição (POS_A) e grava os dois, junto com BKP, num arquivo. Assim você não depende da memória do terminal.

bash
ARQ_A=$(grep -oP "SOURCE_LOG_FILE='\K[^']+" "$BKP")
POS_A=$(grep -oP "SOURCE_LOG_POS=\K[0-9]+" "$BKP")
printf 'BKP=%s\nARQ_A=%s\nPOS_A=%s\n' "$BKP" "$ARQ_A" "$POS_A" > ~/backup_techstore/marcos.txt
cat ~/backup_techstore/marcos.txt
O que você deve ver

Três linhas: BKP= com o caminho do backup, ARQ_A= com um nome como binlog.000003 e POS_A= com um número. Confira se os números batem com a linha que você leu no passo anterior.

Se algo ficou errado

Se o arquivo tiver 0 bytes, se a última linha não for Dump completed ou se ARQ_A ou POS_A ficarem vazios, apague o arquivo e refaça o 1.2:

bash
rm "$BKP"

Prática 1 — passo 1.4tempo previsto da Prática 1: 30 min

Cópia conferida

O que faz: simula a cópia fora do local e calcula o código de integridade (SHA-256) do original e da cópia.

bash
cp "$BKP" ~/copia_externa/
sha256sum "$BKP" ~/copia_externa/$(basename "$BKP")
O que você deve ver

Duas linhas, cada uma com um código longo seguido do caminho do arquivo. Os dois códigos devem ser iguais.

Para o checklist 3-2-1-1-0

Em produção, essa cópia iria para outro servidor ou para a nuvem, com credencial separada. Aqui, a pasta copia_externa está no mesmo disco da VM: ela não protege contra a perda da VM. Anote isso.

Para a Entrega 3

O mysqldump não copia os usuários do MySQL (criados na Aula 08), porque eles ficam no schema mysql. Confirme com o comando abaixo, que deve dar 0. Anote.

bash
grep -c "CREATE USER" "$BKP"

Prática 2 — passo 2.2tempo previsto da Prática 2: 20 min

Restaurar numa base separada e cronometrar

O que faz: cria a base vazia loja_teste_restaurada e carrega nela o seu backup, medindo o tempo com time. A loja_teste não é tocada.

bash
docker exec -e MYSQL_PWD="$SENHA" mysql-$USER mysql -uroot -e "
DROP DATABASE IF EXISTS loja_teste_restaurada;
CREATE DATABASE loja_teste_restaurada;"

O que você deve ver

Ao final, três linhas de tempo: real, user e sys. Anote o tempo da linha real.

Prática 3 — passo 3.3tempo previsto da Prática 3: 20 min

Marco B: o instante antes do erro

O que faz: pergunta ao MySQL o arquivo e a posição atuais do log binário e acrescenta os dois (ARQ_B e POS_B) ao marcos.txt.

Registre agora

Rode este passo antes de qualquer erro.

bash
read -r ARQ_B POS_B _ < <(docker exec -e MYSQL_PWD="$SENHA" mysql-$USER mysql -uroot -N -e "SHOW BINARY LOG STATUS")
printf 'ARQ_B=%s\nPOS_B=%s\n' "$ARQ_B" "$POS_B" >> ~/backup_techstore/marcos.txt
cat ~/backup_techstore/marcos.txt
O que você deve ver

O marcos.txt agora com cinco linhas: BKP, ARQ_A, POS_A, ARQ_B e POS_B, todas preenchidas.

MySQL 8.4

No MySQL 8.4 o comando é SHOW BINARY LOG STATUS. Tutoriais antigos usam SHOW MASTER STATUS, que não existe mais nessa versão.

Aplicar o log: mesmo arquivo de log

Use este comando se ARQ_A e ARQ_B forem iguais.

Prática 5 — passo 5.1tempo previsto da Prática 5: 15 min

A senha fora do script

Uma rotina de backup não pode depender de alguém lembrar de digitar comandos. Vamos criar um script que verifica o próprio resultado.

Até agora você passou a senha assim: -e MYSQL_PWD="$SENHA". Enquanto o comando roda, a senha fica visível para qualquer usuário da VM no comando ps.

O que faz: grava a senha num arquivo que só você lê. No script, ela entra no docker exec pelo ambiente, sem aparecer na linha de comando.

bash
mkdir -p ~/bin
( umask 077; printf '%s' "$SENHA" > ~/.techstore_backup_pwd )
ls -l ~/.techstore_backup_pwd
O que você deve ver

Uma linha do ls começando por -rw-------: só você lê e escreve.

Prática 5 — passo 5.2tempo previsto da Prática 5: 15 min

Criar o script

O que faz: cria o arquivo ~/bin/backup_techstore.sh. O script faz o backup, só aceita o arquivo se ele terminar com Dump completed, grava o código SHA-256 e apaga backups com mais de 7 dias.

Cole o bloco inteiro de uma vez.

bash
cat > ~/bin/backup_techstore.sh <<'FIM'
#!/bin/bash
# Backup lógico da loja_teste: verifica o arquivo e guarda 7 dias
set -euo pipefail
umask 077

DESTINO="$HOME/backup_techstore"
CONTEINER="mysql-$(id -un)"
ARQ="$DESTINO/loja_teste_$(date +%F_%H%M).sql"
MYSQL_PWD=$(cat "$HOME/.techstore_backup_pwd")
export MYSQL_PWD

mkdir -p "$DESTINO"
docker exec -e MYSQL_PWD "$CONTEINER" mysqldump -uroot \
  --single-transaction --routines --triggers --events --source-data=2 \
  loja_teste > "$ARQ.tmp"

# Só aceita o backup se o mysqldump chegou até o fim
ultima=$(tail -n 1 "$ARQ.tmp")
if [[ "$ultima" == *"Dump completed"* ]]; then
  mv "$ARQ.tmp" "$ARQ"
  sha256sum "$ARQ" > "$ARQ.sha256"
  echo "$(date '+%F %T') OK: $ARQ"
else
  echo "$(date '+%F %T') FALHA: backup incompleto em $ARQ.tmp" >&2
  exit 1
fi

find "$DESTINO" -name 'loja_teste_*.sql*' -mtime +7 -delete
FIM
chmod 700 ~/bin/backup_techstore.sh
O que você deve ver

Nenhuma mensagem. O terminal volta ao prompt.

Agendar para daqui a 3 minutos

Em produção, a linha seria 0 2 * * * (todo dia às 2h). Para ver o agendamento funcionar sem deixar a rotina ativa, o comando abaixo cria uma execução, daqui a 3 minutos.

O que faz: calcula minuto, hora, dia e mês de daqui a 3 minutos e acrescenta a linha do script ao seu crontab, sem abrir editor.

bash
MIN=$(date -d '+3 min' +%-M); HOR=$(date -d '+3 min' +%-H)
DIA=$(date -d '+3 min' +%-d); MES=$(date -d '+3 min' +%-m)
( crontab -l 2>/dev/null; echo "$MIN $HOR $DIA $MES * \$HOME/bin/backup_techstore.sh >> \$HOME/backup_techstore/log.txt 2>&1" ) | crontab -
crontab -l
O que você deve ver

O crontab -l mostra uma linha com quatro números e um *, seguidos de $HOME/bin/backup_techstore.sh e do redirecionamento para log.txt.

Os cinco campos são minuto, hora, dia do mês, mês e dia da semana.

Enquanto espera os 3 minutos

Responda ao checkpoint. Ir para o checkpoint e depois volte ao passo 5.5.
